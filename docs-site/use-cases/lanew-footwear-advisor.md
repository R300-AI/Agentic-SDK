# LaNew 售鞋顧問

示範導入案例：看 Agentic SDK 如何把門市銷售知識、足型理解與商品推薦整合成可持續優化的售鞋顧問流程。

**問題**  門市售鞋顧問往往依賴資深店員經驗，導致需求理解、推薦邏輯與說明品質難以標準化。  
**解法**  以 Agentic SDK 建立一條可循環的顧問 workflow，讓顧客需求、商品知識與回應生成都能被明確拆成可維護的模組。

## 把購鞋顧問能力帶進零售服務現場

在鞋類零售場景裡，顧客並不是在問一個單純 FAQ。有人想找久站鞋，有人想找通勤鞋，有人帶著足底壓力、足弓支撐或寬楦需求進店，也有人其實只是需要一個更容易理解的推薦理由。真正困難的地方，不是把商品資料列出來，而是把顧客需求翻譯成一條可以持續追問、持續收斂、最後能交付購買建議的互動流程。

Agentic SDK 在這裡的角色，不是取代銷售顧問，而是把顧問行為中的關鍵環節結構化。當顧客問題進來時，系統先理解需求，再決定是否需要回查鞋款、尺寸、足型或服務規則，最後輸出一段能真正說服顧客的推薦說明。若顧客追問新的限制條件，流程再進入下一輪，而不是回到零散的查表與人工重組。

## 門市售鞋最難的不是回答，而是判斷要回答什麼

售鞋顧問的挑戰通常來自三個層次。第一是需求本身常常含糊，例如顧客只說「最近腳很痠」或「想找比較好走的鞋」，這種話需要被進一步翻成久站、通勤、恢復、支撐或尺寸等可操作條件。第二是商品知識分散，鞋款型錄、尺寸表、材質說明、門市服務規則與庫存狀態常常分散在不同來源。第三是顧客要的不只是結論，而是理由，系統必須講清楚為什麼某款鞋適合這個人。

如果沒有明確的流程設計，系統很容易退化成兩種極端：不是只會把條目列出來，就是過度生成看似合理、實際卻脫離商品規格的推薦話術。這正是 Agentic SDK 能介入的地方。

## Agentic SDK 如何把顧問流程拆成可維護的系統

在這個示範場景中，`Perceive` 先處理顧客輸入，辨識這一輪究竟是在談通勤、久站、恢復、尺寸還是足型支撐。`Plan` 則負責判斷當前資訊夠不夠，是否要先回查鞋款資料、門市規則或尺寸換算。`Retrieve` 對接的是鞋款型錄、材質描述、足型建議、試穿與保養知識，以及必要時的門市限制。`Action` 最終不是只回傳一組 SKU，而是產出一段顧客能直接理解的推薦說明。若回應沒有真正解決問題，`Reflect` 還可以把流程拉回檢索或重新回答。

這種拆法的價值在於，每一個能力點都能獨立改善。當商品資料擴充時，優先升級的是 `Retrieve`。當顧客意圖辨識不足時，調整的是 `Perceive`。當推薦說法不夠像資深店員，優化的是 `Action`。整個顧問系統因此不再是一個難以維護的大 prompt，而是一條可以漸進迭代的 workflow。

## 從商品知識到可交付的推薦說明

想像一位顧客走進門市說：「我每天站很久，最近腳跟很痠，想找通勤穿的鞋。」在這種情境下，Agentic SDK 不會直接跳到推薦，而是先把這句話拆成久站、腳跟壓力與通勤三個條件。接著 `Plan` 判斷需要查商品知識，`Retrieve` 回收合適的鞋款條目、支撐特性與尺寸建議，最後由 `Action` 整理成像「推薦 A 款與 B 款，原因是中底緩震較強、鞋跟穩定性較高，較適合長時間站立後仍需要通勤穿著」這種可交付說法。

這種回答方式，才接近真實門市的顧問價值。系統不是在輸出資料，而是在輸出帶有判斷依據的建議。若顧客下一輪追問「那寬腳適合嗎？」或「有沒有比較正式一點的外型？」，流程就再回到 `Perceive`，用新的限制條件重新推進，而不是整段重來。

## 為什麼這種場景適合用 Agentic SDK

LaNew 售鞋顧問這類應用，最適合的不是單一 completion API，而是能把理解、決策、檢索與回應分開治理的 agent workflow。Agentic SDK 的價值在於它不是只幫你「回答」，而是幫你把整個回答過程變成可觀察、可調整、可替換的系統。對零售團隊來說，這意味著推薦邏輯能逐步沉澱，門市知識能逐步結構化，而不是綁死在單一提示工程或單一模型版本上。

實作時，入門可以從 `InputPerceive + KeywordRetrieve + CompletionAction` 起步；當商品資料量擴大、顧客條件更多、對話輪次變長，再逐步升級到 `LLMBasedPerceive`、`SemanticRetrieve` 與 `ReflexionReflect`。這種分階段導入方式，也更接近企業真實上線流程。

## 從單店顧問走向可擴展的零售服務層

一旦這條流程穩定運作，Agentic SDK 的角色就不只是一個門市問答器，而是零售服務層的基礎。它可以往上接會員歷史、足測資料、庫存系統與促銷規則，往下接門市平板、官網導購或客服入口。也就是說，LaNew 售鞋顧問不是一個孤立功能，而是把產品知識、服務知識與顧客互動串成同一條 agent workflow 的起點。

真正決定落地品質的關鍵，仍然是資料。鞋款規格、尺寸對照、足型建議與門市規則如果不完整，再好的生成模型也只會把錯誤說得更流暢。因此這個案例想強調的不是「模型多強」，而是 Agentic SDK 如何讓一個零售顧問場景有了可持續維護與擴展的系統骨架。
