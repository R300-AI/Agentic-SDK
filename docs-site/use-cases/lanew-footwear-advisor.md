# LaNew 售鞋顧問

這個實施例把 Agentic SDK 用在門市售鞋顧問情境。核心目標不是單純回答 FAQ，而是讓系統能根據顧客需求、足型資訊與商品知識，產出可交付給顧客的推薦與說明。

## 場景目標

LaNew 售鞋顧問面對的任務通常包含三件事：先理解顧客要解決什麼問題，再從鞋款資料與服務知識中找出合適選項，最後把推薦原因說清楚。若顧客追問尺寸、足弓支撐、穿著情境或保養方式，系統還要能把上一輪回應帶入下一輪理解。

## 建議流程拆法

在這個場景中，`Perceive` 應優先負責辨識顧客意圖，例如是要找通勤鞋、久站鞋、運動恢復鞋，還是要處理足底壓力與尺寸疑問。`Plan` 再決定這一輪是先查商品知識，還是可直接根據已知條件回覆。`Retrieve` 主要面向鞋款型錄、尺寸表、材質說明、足型建議與門市服務規則。`Action` 要輸出可閱讀的推薦說明，而不只是列 SKU。若顧客對推薦不滿意，`Reflect` 可以引導流程回去補查商品條件或重新整理回答。

## 建議資料來源

- 商品型錄：鞋款名稱、尺寸、楦頭、足弓支撐、材質、使用情境。
- 顧客條件：腳長、寬度、足弓型態、久站時長、通勤習慣、過往購買紀錄。
- 服務知識：試穿建議、尺寸換算、保養方式、退換貨規則。
- 門市限制：是否有庫存、哪些店型提供足測或加值服務。

## 推薦模組組合

- `Perceive`：若只做最小入口，可從 `InputPerceive` 起步；若要辨識更細的購鞋需求，較適合用 `LLMBasedPerceive`。
- `Plan`：用 `ReActPlan` 判斷是否需要先查鞋款資料、尺寸資訊或服務規則。
- `Retrieve`：入門可用 `KeywordRetrieve` 接商品條目；若資料量大或要結合顧客歷史，較適合 `SemanticRetrieve`。
- `Action`：若要產生自然語言推薦說明，使用 `CompletionAction`；若只是內部工具回傳條目，可先用自訂 action。
- `Reflect`：在高單價或高信任場景下，可加入 `ReflexionReflect` 重新檢查推薦是否有回答到顧客真正需求。

## 一輪對話示例

顧客可能先說：「我每天站很久，最近腳跟很痠，想找通勤穿的鞋。」系統先在 `Perceive` 抽出久站、腳跟壓力、通勤三個條件；`Plan` 判斷需要查商品知識；`Retrieve` 找出適合久站、具緩震與支撐的鞋款；`Action` 再整理成像「推薦 A 款與 B 款，原因是中底緩震較強、鞋跟穩定性較高」這種可交付回答。若顧客接著追問「那寬腳適合嗎」，下一輪再回到 `Perceive` 處理新的限制條件。

## 落地注意點

這個場景最容易失真的地方不是語言生成，而是商品知識不完整。若鞋款規格、尺寸對照或庫存條件不準，回答再流暢也會誤導顧客。因此實作優先順序通常是先把 `Retrieve` 的商品資料與服務規則整理乾淨，再調整 `Perceive` 與 `Action` 的表達品質。
