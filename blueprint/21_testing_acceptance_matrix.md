# Testing and Acceptance Matrix

## 目的

這份文件定義 Playground V2 的驗收不只看功能正確，也看建立者與第一線是否真的能上手。

## 驗收分層

1. 功能驗收
2. 角色驗收
3. 第一分鐘上手驗收

## 功能驗收

### Builder

1. 可建立最小三模組 Workflow。
2. 可建立注入 OpenAI client 的 Workflow。
3. 可建立 custom action 類型 Workflow。
4. 可生成與同步 `python_source`。

### Runner

1. 可執行 Agent。
2. 可依權限保存或回 Builder。
3. 可顯示結果、依據與下一步。
4. 可於需要時展開 `查看依據`。

## 角色驗收

### 建立者

1. 能完成 Builder 設定。
2. 能從 Builder 進 Runner 預覽。
3. 能判斷目前效果是否適合交付。

### 直接使用者

1. 不需接觸 Builder。
2. 打開 Runner 後即可開始任務。
3. 不需理解 workflow/module/source。

## 第一分鐘上手驗收

這一節屬於高價值可用性驗收目標；若 PoC 當前階段無法完整做到，至少應作為後續優化方向，而不強行阻塞基礎功能驗收。

### 30 秒驗收

使用者在 30 秒內應能理解：

1. 這頁能幫他做什麼。
2. 他第一步要做什麼。

### 60 秒驗收

使用者在 60 秒內應能：

1. 完成第一次有效輸入。
2. 看到第一個可理解結果。

### 第一次結果後驗收

使用者在第一次結果出來後應能：

1. 理解是否可直接採用。
2. 找到下一步。
3. 在需要時找到 `查看依據`。

## 角色化情境樣本

1. 門市 / 銷售
2. 客服 / 櫃台
3. 行政 / 助理
4. 照護 / 審查
5. 外部顧客

## 角色化驗收重點

### 門市 / 銷售

1. 是否能快速看到推薦結果。
2. 是否能理解推薦理由。
3. 是否有可直接引用的下一句說法或下一步。

### 客服 / 櫃台

1. 是否能快速看到可直接採用的回覆內容。
2. 是否能在需要時展開依據。
3. 是否知道接下來該補問、重試或升級處理。

### 行政 / 助理

1. 是否能看懂主輸入欄位。
2. 是否不必依賴聊天就能完成主要任務。
3. 是否能清楚看懂結果摘要。

### 照護 / 審查

1. 是否能看懂結論與理由。
2. 若任務風險較高，是否適當顯示可採用等級。
3. 是否能在需要時查看依據。

### 外部顧客

1. 是否不會先看到建立者語言。
2. 是否知道這個頁面能幫他做什麼。
3. 是否不需理解系統背景就能完成輸入與取得結果。

## PM 驗收標準

1. 是否存在功能正確但第一分鐘無法上手的頁面。
2. 是否有角色在不經培訓下仍無法完成任務。
3. 是否有結果缺少可採用判斷與下一步。
