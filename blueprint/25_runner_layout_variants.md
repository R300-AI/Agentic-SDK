# Runner Layout Variants Specification

## 目的

這份文件定義 Runner 不應只有單一主版型。若所有 Agent 都共用同一種「聊天頁 + 側欄」結構，第一線採用時最常見的問題是：

1. 需要填表的任務被硬塞成聊天
2. 需要快速看結論的任務被迫先看長對話
3. 建議型任務沒有足夠好的結果呈現

## 核心結論

Runner 內部設計可使用三種版型模板：

1. `chat_first`
2. `form_first`
3. `result_first`

這三種是平台與前端的內部版型工具，不是建立者或第一線使用者一定會看到的產品模式名稱。

## 使用方式

這三種版型模板主要用途是：

1. 幫助設計與前端決定主區重心
2. 幫助系統推定預設 Runner 呈現
3. 幫助建立者在 Runner 預覽時判斷實際效果是否自然

它們不是 Builder 必填選項，也不是所有 Agent 都要顯性提供切換。

建立者優先面對的應是任務 archetype，而不是這些內部版型名稱。

## Variant A: Chat-First

### 適合任務

1. 問答型
2. 顧問型
3. 客服型
4. 逐步追問型

### 主區結構

1. 上方輕量任務說明
2. 中央對話流
3. 下方輸入區與附件區
4. 次層可展開結果摘要或依據

### 使用者反饋風險

1. 如果結果其實更適合卡片呈現，純聊天會太碎
2. 若依據過深藏，使用者不敢信

## Variant B: Form-First

### 適合任務

1. 評估型
2. 填報型
3. 行政流程型
4. 醫護 / 檢核 / 審查型

### 主區結構

1. 上方任務標題與說明
2. 中段結構化輸入區
3. 送出後下方或右側顯示結果卡
4. 對話僅作補充，不是主體

### 使用者反饋風險

1. 若表單過長，現場人員會抗拒
2. 若結果不夠清楚，會像只是填完一張表

## Variant C: Result-First

### 適合任務

1. 推薦型
2. 決策支援型
3. 分析摘要型
4. 主管 / 審閱型

### 主區結構

1. 上方任務與輸入摘要
2. 中央大面積結果摘要板
3. 下方或側邊為依據、附件與歷史
4. 補充互動入口退到次層

### 使用者反饋風險

1. 若缺少輸入引導，使用者不知從何開始
2. 若沒有依據層，會顯得武斷

## 版型選擇規則

Runner 不應靠固定案例名選版型，而應依輸入契約、輸出契約與可揭露能力決定。

### 任務 archetype 與版型的關係

建立者比較容易理解的是任務 archetype，例如：

1. 問答 / 顧問型
2. 表單評估型
3. 推薦型
4. 摘要 / 判讀型

平台可用這些 archetype 幫助建立者理解方向，但真正落地時，仍須回到既有 Workflow / Modules 組合來推定版型。

### 判斷層級

每個 Agent 可對不同版型有三種適配層級：

1. `preferred`
2. `supported`
3. `fallback`

其中 `chat_first` 應作為最常見的通用 fallback。

### 若符合以下條件，優先 `chat_first`

1. 任務需要多輪追問
2. 輸入主要是自然語言
3. 結果以對話形式即可理解

若沒有更明確的結構化輸入或結構化結果訊號，系統可先以它作為預設推薦。

### 若符合以下條件，優先 `form_first`

1. 任務輸入有固定欄位
2. 使用者需要快速填寫
3. 輸入完整性比對話自由度更重要

若沒有結構化輸入契約，則不應把它當主版型。

### 若符合以下條件，優先 `result_first`

1. 使用者最在意先看結論
2. 結果可做成摘要卡、表格或清單
3. 依據與下一步比對話本身更重要

若結果本質仍只是單段自然語言回覆，則通常只適合作為 supported，而非 preferred。

## 預設決策方式

最合理的產品流程不是讓建立者先選模板，而是：

1. 系統依 workflow 特性推定一個推薦版型
2. 建立者進 Runner 預覽
3. 若實際效果不自然，再由後續設計或平台策略調整

### MVP 版型決策原則

1. 不額外保存一份獨立版型設定
2. 先依既有 Workflow / Modules 特性自動推定
3. 讓建立者透過 Runner 預覽驗證，而不是在 Builder 額外學一套版型術語

## 典型第一線反饋

### 門市人員

`我不想一直聊天，我想先看到推薦。`

對應：

1. 優先 `result_first`
2. 主區先給推薦卡、理由、下一句建議話術

### 客服人員

`我想快速得到可直接回覆的內容。`

對應：

1. 優先 `chat_first`
2. 補上回覆卡與快速操作

### 行政 / 櫃台

`我比較像在填表，不是在跟 AI 對話。`

對應：

1. 優先 `form_first`
2. 對話退為補充互動

## MVP 任務 archetype 對應矩陣

| 任務 archetype | 建立者直覺理解 | 推薦內部版型 | 主輸入方式 | 主結果容器 | 補充層 |
| --- | --- | --- | --- | --- | --- |
| 顧問 / 問答型 | 讓 Agent 和人對話並逐步給建議 | `chat_first` | chat | 對話回覆或摘要回覆 | 依據、下一步 |
| 表單評估型 | 先填資料再看結果 | `form_first` | structured input | 摘要卡 / 結論板 | 依據 |
| 推薦型 | 先給我推薦與理由 | `result_first` | chat 或簡短欄位 | recommendation card | 理由、依據、話術 |
| 回覆助手型 | 給我一段可直接回覆的內容 | `chat_first` | chat | reply draft card | 理由、下一步 |
| 摘要 / 判讀型 | 幫我整理與判讀資訊 | `result_first` | chat / structured / attachment 其一為主 | 摘要板 / 判讀卡 | 依據、可採用等級（若需要） |

## PM 驗收標準

1. Runner 是否至少有三種內部主版型模板。
2. 版型選擇是否由輸入/輸出特性驅動，而不是 by use case 名稱。
3. 系統是否可推定推薦版型，而不是要求建立者必選。
4. 第一線角色是否能從最終頁面快速判斷如何開始任務。
