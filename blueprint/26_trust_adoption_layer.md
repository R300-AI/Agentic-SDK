# Trust and Adoption Layer Specification

## 目的

這份文件定義 Playground V2 若要被第一線採用，除了功能和頁面之外，回應內容本身還必須有一層輕量、低干擾的信任揭露設計。

## 核心問題

基層使用者不採用 Agent，常見原因不是功能不足，而是：

1. 不知道結果能不能直接用
2. 不知道為什麼系統這樣建議
3. 不知道出錯時怎麼補救
4. 不知道下一步該做什麼

## 信任層四段式

每個 direct-use Runner 至少應支援以下四層資訊：

1. `結論`
2. `原因`
3. `依據`
4. `下一步`

### 結論

使用者先看到可以採用的主要建議或結果。

### 原因

說明為什麼會得到這個結論。

### 依據

讓使用者知道建議是根據哪些輸入、資料或來源。

這一層預設不應做成獨立頁或重面板，而應優先做成回應區塊下方的可展開小功能。

## 呈現方式

信任層最合適的呈現方式是：

1. 回應或結果卡下方的 `查看依據` / `參考來源` / `為什麼這樣建議`
2. 點開後才顯示來源片段、理由摘要、引用內容
3. 不需要的使用者可完全忽略，不干擾主任務

### 下一步

告訴使用者現在可以怎麼做，例如：

1. 直接採用
2. 補充資料再試一次
3. 轉人工 / 升級處理
4. 回報結果不適用

## 低風險操作原則

第一線使用者最需要的是「不容易犯錯」。因此 Runner 應具備：

1. 清楚的開始點
2. 單一主 CTA
3. 可預期的提交結果
4. 發生問題時的補救建議
5. 不讓使用者誤觸建立者能力

## 採用層對不同角色的意義

### 門市 / 銷售

重點：

1. 快速看建議
2. 知道怎麼對客人說
3. 有簡潔理由可引用

### 客服 / 櫃台

重點：

1. 快速產出可回覆內容
2. 有升級或補問下一步
3. 有簡單依據可自保

### 行政 / 照護助理

重點：

1. 表單清楚
2. 結果格式穩定
3. 不必理解 AI 結構

### 外部顧客

重點：

1. 頁面要像服務，不像系統
2. 不要出現建立者語言
3. 要清楚知道系統目前能幫什麼

第一線回饋如何蒐集、流回建立者、再導向產品修正，屬於平台工程與營運閉環議題，不是 Runner 主規格的核心責任。

## PM 驗收標準

1. Direct-use Runner 是否能提供結論 / 原因 / 依據 / 下一步四層。
2. 依據是否以回應下方的小型可展開功能呈現，而不是重面板或獨立頁。
3. Agent 頁是否先像服務頁，再像系統頁。
