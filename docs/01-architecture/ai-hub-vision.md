# AI Hub Vision — TSiP 落地藍圖中的雙核心定位

> 受眾：架構決策層、跨單位協作窗口
> 目的：說明 Agentic SDK 在工研 AI 生態系中扮演什麼角色,以及與其他子系統的邊界。

## 一、問題脈絡

工研 AI 生態系 TSiP 國產晶片落地面臨兩個共通死穴:

1. **缺乏共通部署方法**:晶片 × 模型的組合爆炸,99% 開發者在第一步就遇到相容性瓶頸,市場信心不足。
2. **營運多停留在專案等級**:每個整合案都是一次性的「特殊解」,沒有可重複的工程基礎設施。

任何單一晶片廠或單一應用商都無法獨自解決這兩個問題——這是「中間層基礎設施」的天然位置。

## 二、AI Hub 的雙核心定位

```
┌─────────────────────────────────────────────────────────────┐
│ 應用端 (Application Layer)                                   │
│ 製造 (T500) / 醫療 (R300) / 跨領域整合商                      │
│ 使用 LangChain / AutoGen / 任意 OpenAI SDK                  │
└─────────────────────────────────────────────────────────────┘
                            ↓ 標準 OpenAI 相容 API
┌─────────────────────────────────────────────────────────────┐
│ B. Agentic SDK (本專案)                                      │
│ ─ 跨節點 Agent 編排                                          │
│ ─ 動態異質 Offload                                           │
│ ─ 可視化觀測                                                 │
└─────────────────────────────────────────────────────────────┘
                            ↓ 只信任通過認證的模型
┌─────────────────────────────────────────────────────────────┐
│ A. Model Card / SLA 認證閘道                                 │
│    (上游:amd-ryzen-ai-benchmark)                            │
│ ─ TTFT / Peak Memory / Soak Test 量測                       │
│ ─ 硬體指紋與可重現性                                          │
│ ─ 認證履歷產出                                                │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│ 晶片層 (TSiP 國產晶片 + AMD Ryzen AI + 其他異質硬體)          │
└─────────────────────────────────────────────────────────────┘
```

### Agentic SDK 的升級選擇

Action item 明示 Agentic SDK 的升級路徑:

> **從「API 介面」升級為「邊緣叢集管理協定」**

這个升級是本專案的戰略重心。「OpenAI 相容 API」只是對外採用事實標準的選擇,避免上層生態切換成本;真正的價值在於後端能讓多個模型、多個 Agent 工作流、多個邊緣節點互相協調。

這也是為什麼本階段兩大 Action Item 都聚焦在「叢集管理能力」本身:

1. **上下文管理**:讓多 Agent 工作流能安全地在邊緣叢集上跨節點運作,是叢集管理的最低門檻
2. **部署資源可視化(Multi-Model Dashboard)**:讓叢集管理狀態可視、可驗證,是讓「協定」這個抽象變成可操作產品的關鍵

動態 Offload、ReAct 路由這些是叢集管理協定的內部機制,不是對外承諾。

### A 與 B 的分離理由

兩者拆為獨立儲存庫,而非同一套程式碼,基於三個工程理由:

1. **演進節奏不同**:Benchmark 方法學與硬體驅動綁定,變動頻率低;Agent 編排與上層框架綁定,變動頻率高。同倉庫會互相拖累。
2. **責任邊界清晰**:認證閘道的失敗模式是「量測失準」,需要硬體實驗環境;SDK 的失敗模式是「編排崩潰」,需要應用負載模擬。兩者測試環境完全不同。
3. **可替換性**:未來若有第三方提供同等效力的認證履歷(例:廠商自送 MLPerf 報告),SDK 應能直接消費,不需強綁特定 Pipeline。

## 三、商業假設與現階段對外可見成果

AI Hub 的商業價值建立在一個核心假設上:

> **「通過認證的模型,可被任何 OpenAI SDK 直接調用」這條最窤路徑能跑通,且多模型部署狀態能在 Dashboard 上被即時看見。**

只要這條路徑成立,以下衍生價值才有立足點:
- 晶片廠商有動機投資認證,因為認證後立即可被全球 Agent 生態系消費
- 系統整合商願意採用 SDK,因為不需重寫應用程式
- 企業客戶接受 SDK,因為可隨時切換到非國產備援方案

現階段的對外可見成果以 **Multi-Model Dashboard** 為主軸——它是「邊緣叢集管理協定」唯一能讓非技術層的決策者被說服的載體。API 只能證明「能跳」,Dashboard 才能證明「可調度」。

## 四、本專案不碰的範圍

| 範疇 | 歸屬 |
|------|------|
| SLA 自動化基準測試 Pipeline | 上游 `amd-ryzen-ai-benchmark` |
| 晶片驅動、編譯器、底層 Runtime | 各晶片廠商 |
| 終端應用程式 UI | 整合商或客戶 |
| 模型訓練、微調 | 模型供應方 |

任何試圖把上述能力塞進本專案的需求,都應該被拒絕,以免邊界擴散導致核心失焦。

## 五、PoC 允許的例外

潔淨架構是長期方向,但 PoC 階段(M0–M3)為了保住最窤路徑能跑通,以下幾個地方暫時鬆綁。這節是「合規違反」的清單——所有列在這裡的妥協,都必須在 MVP 階段(M4+)補強;沒列在這裡的妥協,屬於技術債,不是允許的例外。

| # | 暫時做法 | 最終目標 | 允許的理由 | 補強時點 |
|---|---------|---------|-----------|---------|
| E-1 | **模型 × 硬體靜態綁定**:Action 節點透過 `UPSTREAM_API_BASE_URL` 直接綁一個 NPU 上游 | 動態異質 Offload(NPU / GPU / CPU 之間依負載即時調度) | 動態 Offload 必須先有跨硬體 SLA 比較表,而上游 Model Card 認證才剛從單一硬體開始;先單點打通,再展開 | M4 起待 R300 額外硬體就位 |
| E-2 | **Active / Archived context 單行程 in-memory**:`agentic_sdk/context/active_store.py` 直接用 dict | 多 Gateway 副本共享一份 Active context(Redis / 分散式 KV) | 跨副本一致性語義會綁定特定 KV 廠商,在「第二台 Gateway 出現」前不投資 | 出現第二台 Gateway 副本時 |
| E-3 | **Plan / Reflect 在無 Foundry 金鑰時降為 MockFoundry**:`workflow_force_mock_foundry=true` 路徑 | Plan / Reflect 必須使用實際 Azure Foundry 模型 | 讓使用者在沒拿到專案維護者 Foundry 金鑰前仍能驗證五節點軌跡,避免「環境裝完才發現跑不起來」的勸退體驗 | MVP 前評估;若改為內建 SLM 則此例外解除 |
| E-4 | **`/v1/chat/completions` 只回非串流**:Gateway 把整個 Workflow 跑完才回應 | OpenAI 標準 `stream=true` 串流 | 串流要求 Workflow 內部所有節點能以 callback 釋出部分結果,違反「節點批次更新 Active context」的當前語義;先讓非串流 + `x-agentic-metadata` 把節點軌跡透出 | M4 起,搭配 ReAct 路由細化 |
| E-5 | **單機部署、無 Auth / 無 Quota**:Gateway 不驗 API key、不限流 | 多租戶 Auth + 配額管理 | PoC 在受信任邊緣節點內,沒有外部曝露面;Auth/Quota 屬叢集管理協定的「對外」面向,先把「對內編排」做完 | 對外發布前(M5 前) |
| E-6 | **Telemetry 走 in-memory RingBuffer**:`agentic_sdk/observability/ring_buffer.py` 為唯一後端 | 標準 OpenTelemetry exporter(OTLP / Tempo / Jaeger) | RingBuffer 已對齊 OTEL semantic conventions,事件 schema 不變;後續換 exporter 不影響上層 | Multi-Gateway 副本出現時(同 E-2) |

每一條都必須在子目錄的設計文件中標注「**此處違反潔淨架構,對應 E-X**」並附對 `ai-hub-vision.md §五` 的回連,避免日後接手者把妥協誤認為設計意圖。
