# 16. 天花板是對話被衡量的標準，不是請求大小的保證

Date: 2026-09-23

## Status

Accepted

部分取代 ADR-0012。

## Context

ADR-0012 讓記得住自己的記憶把最舊的對話合成成主題，門檻是建構記憶時給的一個數字。那一版在 Consequences 裡留了兩件事給後面：索引還沒有被送進提示詞，以及「真正的硬上限屬於流程層」。

把流程層的上限加進來之後，同一次執行裡出現了兩個數字：`Gates.max_prompt_tokens` 管一個請求能有多大，`FileMemoryStore` 的 `compaction_threshold_tokens` 管對話多長就該合成。兩個數字沒有定義關係，會得到一個誰都不想要的結果：只設天花板的人拿到的是訊息在接縫上被切掉，對話裡那一段話就此消失，而合成從來沒有被觸發過——合成的意義正是那段話留得下來。

還有三件事在加上天花板之後才變成要決定的：超出時**放掉什麼**、放掉的**順序**，以及**放到哪裡為止**。

兩家標竿的做法不同。Codex 有一個明確的優先級棧（system > tools > developer > user > history），配合 Compaction 與 Observation Masking。Anthropic 的做法是在接近上限時做伺服器端壓縮，預設 150K。共同點是：壓縮先於丟棄，而最該保住的是指令與這一輪。

## Decision

**兩個階段，順序固定：先合成，再裁切。** 記憶在自己的出口檢查長度並合成主題，那一段話因此留在索引裡；合成之後還是裝不下，才在組好訊息之後從對話最舊的一端放掉。順序反過來的話，被裁掉的內容還沒被合成就已經不在了。

**一個天花板，兩個位置生效。** 建構記憶時給過門檻的，那個數字贏——有人替那個記憶選過它。沒給過的，天花板變成它的門檻。拿天花板的一個比例去比對話，那個比例會是一個編出來的數字，所以不那樣做：對話只是請求的一部分，把對話壓到天花板本身並不保證請求裝得下，也不需要保證，裝不下的部分交給後面的裁切。

**放掉的只有這一輪之前的對話，最舊的先放。** 系統提示（含索引）、檢索證據與這一輪的內容不動。索引不動的理由和主題一樣：規劃查不到它看不見的主題，切掉索引失去的是記憶本身，不只是措辭。

**「這一輪」是最後一次模型發言之後的全部內容，與使用者最後說的那一句，兩者取較早的位置。** 只看最後一則使用者訊息不夠：規劃模組會在問題後面補一則使用者角色的技能文字，那樣問題本身會變成可放掉的。只看最後一次模型發言也不夠：呼叫工具的那一輪結束在工具回覆上，最後一則訊息既不是問題也不是使用者發的。取較早的那個位置在這三種情形下都對。

**工具回覆跟著叫它的那則訊息一起放掉。** 單獨留著是一個沒有問題的答案，有些端點直接退件。

**`0` 是最嚴格的天花板，不是沒設。** 沒設寫成 `None`。把 `0` 當成沒設，等於讓一個想把話關到最小的人拿到完全不裁切的結果。

**工具定義計入，圖片不計入。** 工具定義不在訊息清單裡，但照樣送出去，不算會少算一整組工具的量。圖片相反：一則帶圖的訊息是一串 parts，圖片那一格裝的是 data URI，把整串轉成字串來數等於把那段編碼當成模型要讀的字，一張圖會把整段對話擠掉。端點怎麼替圖片切塊是端點自己的事，在這裡填一個數字就是把編出來的數字講成量出來的。

**天花板不是請求大小的保證。** 對話全部放掉之後還是超出時，請求照樣送出去。切進指令、證據或問題會改變這一輪在問什麼，而端點退件比回答一個沒有人問過的問題清楚。

考慮過並否決的做法：

- **在天花板底下再切一個比例給對話。** 比例要嘛是編的，要嘛要對每一種模組各調一次；兩者都比「對話盡量讓，讓完還是超出就送出去」難解釋。
- **裁切到裝得下為止，必要時切進系統提示。** 那會讓模組在不知情的情況下照著半截指令回答，比端點退件難查得多。
- **只做裁切，不接合成。** 那正是 #38 第一版的行為，代價是設了天花板的人永遠等不到合成。
- **把兩個數字合成一個，刪掉記憶自己的門檻。** 記憶可以不在流程裡用，那時沒有 `Gates` 可以讀。

## Consequences

ADR-0012 的三項 Consequences 到此結束：「索引還沒有被送進提示詞」、「索引還沒有人讀」都已落地，索引以 `remembered_topics:` 併進系統提示那一層；「真正的硬上限屬於流程層」落地了，但它不是硬上限——上面那一條寫明了為什麼。

**`compaction_threshold_tokens` 還是建構記憶時的一個參數，不在宣告層。** `max_prompt_tokens` 已經在 `GateConfig` 裡，記憶的門檻還沒有；把記憶搬進宣告層與建構器屬於下一份工單。在那之前，用宣告層建立流程的人只能透過天花板間接設定它。

**每一次組訊息都要數一次，超出時還要反覆數。** 裁切迴圈每放掉一則就重數一次整個請求。對話很長又天花板很低時，這是一輪裡最貴的純 CPU 工作。先量再換做法。

**估算沿用 ADR-0012 的算法，也沿用它的不確定性。** CJK 約一個字一個 token，其餘約四個字一個。天花板因此是一個約略的界線。

**`budget_exhausted` 這個停止原因仍然沒有人發出。** 超出天花板不會中止一輪，只會讓對話變短。那個停止原因留給真正用完可用量的情形。
