# 17. 記憶是宣告出來的，不是走訪出來的

Date: 2026-09-23

## Status

Accepted

## Context

組裝設定裡有五個模組與一組 Gates，記憶不在裡面。用宣告層建流程的人因此拿不到跨對話記憶：`WorkflowConfig` 組出來的 `Workflow` 一律是只看這一段對話的那一種，要別的只能繞過宣告層自己 `Workflow(memory_type=...)`。

建構器那一邊的狀況更直接。Q1 一直顯示「承接前文問答」，一直標著「預覽中」、一直按不下去。那個鎖有過它的理由——底下確實沒有東西——而 #34 與 #37 之後底下有了。

要把它接起來，有三件事得先決定：記憶在宣告層長什麼形狀、種類的值命名什麼、以及哪些設定問場域的人、哪些由部署給。

## Decision

**記憶是組裝設定自己的一個欄位，形狀和模組一樣。** `WorkflowConfig.memory` 是一個 `MemorySpec`，有 `kind` 與 `params`，和 `ModuleSpec` 同一個樣子——那是寫過一份設定的人已經認得的形狀。它不進 `modules` 那本字典：那本字典是走訪會經過的五格，多放一格會變成一個流程永遠不會走到的模組。記憶不是流程上的一站，它是每一站讀寫的那個東西。

**種類命名記憶型態，不命名後端。** `in_context` 與 `cross_context`，就這兩個，因為詞彙表裡的記憶型態就是這兩種。寫 `file` 或 `sqlite` 會讓一份去年存下來的設定在後端換掉的那天失效，而換後端是遲早的事。

**東西寫在哪裡決定跑哪一個實作。** 給了地方就寫在那裡，程序結束後還在；沒給地方就留在行程的記憶體裡，重啟就沒了。這樣的話，一個什麼都還沒設定的部署照樣啟動得起來，而不是拿到一個錯誤訊息。代價是「跨對話」這件事在沒給地方的時候只跨得了對話、跨不了重啟——所以建構器不提供那一個選項（見下）。

**建構器只問場域的人答得出來的。** Q1 底下問兩件事：要不要把最舊的內容合成成主題，以及累積到多少就合成一次。這兩件事關於這個 Agent 要怎麼做事，問的人答得出來。

**記憶根目錄與端點憑證由部署給，不存進 Agent。** 根目錄是機器的性質，答 Q1 的人不在那台機器前面，而一份存著目錄路徑的設定搬到另一台機器就指向一個不存在的地方。憑證走既有的金鑰保管那條路，和其他每一個端點一樣。

**記憶體版實作不列進建構器的選項。** 選了「承接前文問答」卻在重啟後發現什麼都沒留下，是被告知了錯的事。它留著當沒指定地方時的退路，不留著當一個選擇。

**記憶是一個需要端點的新角色，條件是它要合成。** 把舊的對話合成成一則主題是一次模型呼叫，所以部署要綁一個端點給它——和輸入解析器、模型回覆器、規劃檢核器同一條路。只是承接前文不需要模型，所以沒開合成就不問。這個角色不靠可達性判斷：記憶不是模組，不在任何一條路徑上。

考慮過並否決的做法：

- **記憶當成第六個模組放進 `modules`。** 走訪只有五格，第六格永遠不會被走到；而把它塞進五格之一會排擠掉那一格真正的模組。
- **在 Q1 直接問記憶寫在哪裡。** 答 Q1 的人在瀏覽器前面，不在伺服器前面。
- **種類寫成 `file` 與 `in_memory`。** 那是把後端當成使用者的選擇，換後端就要改每一份存下來的設定。
- **沒給地方就拒絕建立。** 一個還沒設定儲存位置的部署會完全啟動不了，而它其實可以先跑起來。

## Consequences

**`in_context` 交回的是類別，`cross_context` 交回的是建好的那一個。** 前者每一次執行各自建一個，本來就只看這一段對話；後者建一次、各次執行共用，那正是它存在的理由——跨對話的範圍由 `session_id` 在裡面分。

**`Workflow(memory_type="cross_context")` 這個字串仍然是記憶體版。** 字串沒有地方夾帶根目錄，所以它只能是沒給地方的那一種。宣告層要寫在哪裡就用 `MemorySpec(kind="cross_context", params={"root": ...})`。

**建構器的 Q1 表單以前會把記憶種類洗掉。** 表單送出的是那一題底下的設定，不含選擇本身——選擇是按下去的時候另外送的。舊的程式把「沒帶種類」讀成「選了預設那一種」，所以在 Q1 打一個常用問題就會把記憶改回只看這一段對話。那個鎖著的選項讓這件事一直沒有發生過。現在沒帶種類就維持原本選的那一個。

**`ALLOWED_MEMORY_KINDS` 多了一個值，舊的存檔照樣開得起來。** 沒有 `memory` 欄位的存檔讀成 `in_context`，和以前一樣。

**匯出的程式碼把記憶寫進去，根目錄寫成腳本旁邊的一個資料夾。** 匯出的程式跑在哪裡，建構器不知道，所以它寫一個 `./agent-memory` 讓拿到的人改。合成用的端點三項留空：那是部署的答案，猜一個填進去會讓人以為它已經設定好了。只看這一段對話的那一種不寫進去，因為 `Workflow` 不寫也是那樣。

**部署要指定 `PLAYGROUND_MEMORY_ROOT`，而且要落在 `wwwroot` 之外。** App Service 每次部署會換掉 `wwwroot` 底下的全部內容，記憶放在那裡會被下一次發布清空——那正是它存在要避免的事。預設值因此先看 `/home` 在不在，部署流程也把這個設定明確寫進去。這一條是 ADR-0011 就寫下的要求，這份工單才把它接起來。

**那個勾選框是建構器的第一個勾選框，而回填表單的程式沒有處理過勾選框。** 它一律寫 `.value`，勾選框的答案在 `.checked`，所以存檔重開之後每一個開關都顯示成關的，接著下一次表單同步又把「關」存回去。#39 之前沒有勾選框，所以這件事沒有發生過。

**壓縮門檻現在有兩個入口。** 建構器問到的那一個存在 Agent 的設定裡，`Gates.max_prompt_tokens` 那一個由 ADR-0016 的規則接手——記憶自己有數字就用自己的。兩個都沒有就不會合成。
