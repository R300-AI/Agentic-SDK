# 14. 查記憶是每一個 Retrieve 模組共同的底

Date: 2026-09-22

## Status

Accepted

## Context

跨對話記憶落地之後（ADR-0011），有一個問題沒有答案：誰去查它。

原本只有 `SemanticRetrieve` 會。它在自己的 `__call__` 裡呼叫 `state.cross_context_memory()`，把結果和外部來源的命中併在一起。另外兩個查找模組完全不碰記憶。

這讓「這個 agent 記不記得事」取決於一個看起來和記憶無關的選擇。場域人員在建構器第一題選了「承接前文問答」，卻在另一題選了「直接傳遞文字」，結果就是啟用了記憶而什麼也沒發生——而那兩題之間沒有任何提示說它們相關。

第三方自己寫的查找模組更是完全不會有記憶，因為沒有任何地方寫著要接上它。

## Decision

**查記憶放進 `BaseRetrieve`，三個模組都繼承得到。** 它不是一個要另外選的能力，是每一個 Retrieve 模組站著的地板。第三方模組繼承基底就自動有，不必知道記憶怎麼運作。

**模組不知道記憶在哪裡。** 基底從 `state.cross_context_memory()` 問，而那個物件是 `Workflow` 依它自己的設定解析出來的。路徑只有記憶那一格說了算——兩邊各填一次會在填不一樣時查到空目錄，而且不會報錯，只會查不到東西。

**基底提供預設的文字比對查法，有更好的辦法的模組覆寫它。** `SemanticRetrieve` 覆寫 `_memory_hits`，把它手上的 embedder 也帶進查詢。`KeywordRetrieve` 與 `PassThroughRetrieve` 沿用預設，因此不需要任何端點——那正是它們存在的理由。

**「原樣帶過」的意思改成「不查外部來源」。** 記憶照查。記憶不是使用者交給這條流程的外部資料，是這個 agent 自己累積的東西，兩者不同類。沒有配置跨對話記憶時，它的行為和以前完全一樣。

**語意模組的向量索引改成第一次用到才建。** 原本在建構時就讀來源、建 faiss 索引；一次沒有查任何東西的執行不該付這個代價。這一條和記憶無關，但它和基底的改動落在同一個 `__call__` 上，分兩次改會讓同一段程式動兩次。

延後的只有建索引這件事。**缺 embedder 這種設定錯誤仍然在建構時就擋下**——ADR-0011 為根目錄定的原則是「不能用的設定在那一刻就失敗，而不是等到執行到一半」，那條原則在這裡照樣適用；把檢查一起延後會讓一個接錯的 agent 建得起來、在有人等回答時才吐出一次模組失敗。

考慮過並否決的做法：

- **做成第四個查找模組。** 一條流程只掛得了一個 Retrieve，那會變成「要記憶就不能用關鍵字比對」，和把壓縮做成 Reflect 模組同一種毛病（ADR-0012）。
- **做成一個共用函式讓各模組自己呼叫。** 收得掉重複，但給不了保證：新寫的模組忘記呼叫就沒有記憶，而且從模組清單上看不出來誰有誰沒有。
- **讓記憶層自己把內容推給模組。** 那會讓記憶決定查詢的內容，而決定查什麼是 Retrieve 的工作。

## Consequences

`PassThroughRetrieve` 與 `KeywordRetrieve` 的輸出在配置了跨對話記憶時會多一段記憶命中。它們的 `retrieved_snippet` 因此變長，而 `DirectAnswerAction` 直接把它當回覆——所以「原樣帶過加直接作答」這個組合現在會把記憶內容講出來。沒有配置記憶時完全不變。

記憶命中的筆數固定是 `memory_top_k`（預設 3），三個模組共用。`SemanticRetrieve` 用它自己的 `top_k`，維持原本的行為。

`format_memory_hits` 從 `semantic.py` 搬到 `base.py` 並成為公開名字——三個模組都會產出它，格式必須一致。

`SemanticRetrieve._knowledge_base` 在建構後可能是 `None`，要透過 `_ensure_knowledge_base()` 取得。直接讀那個私有屬性的程式會拿到 `None`；測試裡有兩處這樣讀，已經改掉。

`CONTEXT.md` 對 Retrieve 的定義不必改——它在規劃階段就是照這個目標狀態寫的，這份決議只是讓程式追上它。
