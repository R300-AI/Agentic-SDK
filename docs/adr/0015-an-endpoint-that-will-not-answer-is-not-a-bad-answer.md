# 15. 端點不回應和模型答得不好是兩件事

Date: 2026-09-22

## Status

Accepted

## Context

ADR-0010 把模組的失敗統一收到流程層接住，一律記成一筆紀錄交回規劃。那一版刻意不分種類，而它在 Consequences 裡寫明了代價：依失敗種類分流留給另一份工單。

不分種類的代價現在看得到。端點連不上時，規劃拿到一筆失敗紀錄、選了下一步，那一步用的是同一個端點，於是再失敗一次——直到撞上重訪上限。使用者在整個過程中等著，而每一次重試都不可能成功，因為不通的是端點本身。

模型有回應但內容不合用則相反：再問一次通常就好了，那正是規劃存在的理由。

兩家標竿也是分開處理的。Anthropic 對連線錯誤與 5xx 自動退避重試然後拋出，而工具結果不合用是回 `is_error` 交給模型自己處理——同一份 SDK 裡兩條不同的路。

## Decision

**端點那一層自己命名它的失敗。** `agentic_sdk/core/failures.py` 只放一個 `EndpointUnavailable`，什麼都不 import；呼叫端點的那一層在 provider 拋出任何東西時包成它。核心因此分得出這兩種失敗，而不必認得任何一家 provider 的例外型別。

那個模組之所以只放一個類別、什麼都不 import，是因為核心與端點層本來就經由記憶互相 import，放在任何一邊都會繞成一圈。

**重試次數沿用該層 SDK 自己的預設，不另外疊一層。** 呼叫到這裡時它已經重試過了。在上面再加一套重試策略，會讓調過第一套的人看不出實際會重試幾次。

**端點不回應就結束這一輪，不交回規劃。** 停止原因是 `endpoint_unavailable`，交付出去的內容照樣交出。規劃對一個不通的端點做不了任何決定。

**模型有回應但內容不合用照舊交回規劃。** 那是 ADR-0010 定的路，沒有改。

**行動那兩個模組不再自己吞下端點失敗。** `GenerativeAction` 與 `ToolCallAction` 原本把任何例外都轉成一句道歉然後讓流程走完；端點不通時，那句道歉會被當成答案交給使用者，而流程看起來一切正常。現在它們放行 `EndpointUnavailable`，和放行 `WorkflowInterrupted` 同一個道理——兩者都不是這個模組該決定的事。

**反思那一格維持降級。** `PlanCheckReflect` 在模型不可用時回報「這次檢查沒跑」並讓流程繼續，那是它明文寫下的選擇：一個跑不起來的檢查不該擋住使用者拿到答案。檢查是可略過的，答案不是。

考慮過並否決的做法：

- **在流程層按例外型別分類。** 那會讓核心 import `openai`，而這個 SDK 的整個賣點是換一個 OpenAI 相容端點就能跑。
- **在流程層再加一套退避重試。** 兩層重試，實際次數是兩者相乘，沒有人算得出來。
- **端點失敗也交回規劃，靠重訪上限擋住。** 那正是現況，代價是使用者等著看五次必定失敗的呼叫。

## Consequences

`endpoint_unavailable` 是第九個停止原因。ADR-0013 那張表跟著補。

第三方寫的模組現在有一條新規矩：**不要攔 `EndpointUnavailable`**，和不要攔 `WorkflowInterrupted`、`WorkflowAborted` 同一類。攔下來會讓一個不通的端點看起來像這個模組答得不好。

被包過一層的例外，它的訊息裡帶著原始 provider 例外的型別與文字。那段文字只會出現在事件流與 context entry 的 metadata 上（ADR-0010 定的分工），使用者看到的仍然是那一格的中性訊息。

`PlanCheckReflect` 與其他幾個自己捕捉例外的模組仍然會吞下 `EndpointUnavailable`。它們各有明文理由，但這表示「端點不通就結束」不是一條沒有例外的規則——它是流程層的預設，模組可以刻意不照做，而刻意不照做的地方都寫了為什麼。
