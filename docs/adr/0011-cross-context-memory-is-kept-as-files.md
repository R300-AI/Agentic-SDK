# 11. 跨對話記憶存成檔案而不是資料庫

Date: 2026-09-22

## Status

Accepted

## Context

`CrossContextMemory` 這份協定早就在——`append` 寫一筆條目、`search` 按相似度與時近度取回——但唯一的實作 `InMemoryStore` 只活在行程裡。行程一重啟，agent 就什麼都不記得。Playground 建構器第一題那個「承接前文問答」因此鎖著、標「預覽中」：畫面告訴場域人員有這個能力，按下去卻沒有東西。

兩家標竿各站一邊。Claude 存成檔案——專案檔加上自動生成的記憶檔，切成三層，索引那一層每一則約 150 字元。Codex 存進資料庫——SQLite 或 Redis 的對話存儲。兩者都能實作同一份協定，所以這個選擇不是技術可行性的問題，是讀者的問題。

**這裡的讀者是場域人員，不是開發者。** 他在 Playground 上組出這個 agent，接下來要看得出它記住了什麼、並且把記錯的那一則刪掉。這是選項存在的理由，不是附帶的功能。

## Decision

**存成檔案。一則條目一個 markdown 檔。** front matter 放種類、層級、來源（哪一次執行、哪一段對話）與時間，正文就是條目本身。一個人打開它看得懂，刪掉它就是忘掉那一則。

**目錄按流程的名字分，同一條流程的各段對話共用一個目錄。** 這是它跨對話的方式。目錄底下再按層級分一層，各自一個子目錄（目前只有 `raw`），讓一個人要刪掉整批原始紀錄時刪一個目錄就好，也讓主題層不和它們混在一起。

流程的名字由 `Workflow` 說了算——`_resolve_memory` 會用流程的名字覆寫記憶物件上的那一個，而且是在那個物件建好**之後**。所以這個實作把名字做成一個屬性，被賦值時就改讀那個流程的目錄；沒有這一步，一個用某個名字建起來、卻跑在另一個名字底下的記憶會拿著前者的條目往後者的目錄寫。

名字與條目的 id 都會被當成單一路徑名使用，所以其中不能當路徑的字元一律換掉。id 另外有一層保護：單純換字元會讓 `a b` 與 `a-b` 變成同一個檔名、後寫的把先寫的蓋掉，所以不安全的 id 改用它的摘要當檔名，真正的 id 寫進 front matter，不靠檔名讀回來。

**`turns` 仍然只給這一段對話。** 模組讀 `turns` 當前文，讓另一段對話的內容以前文的身分出現在提示詞裡是錯的。跨對話靠 `search`，而 `search` 本來就只按流程的名字過濾、不按對話過濾。這個分工不是這份決議新增的，是既有協定的形狀；寫在這裡是因為「檔案還在」很容易被誤讀成「前文接得回來」。

**保留期是一個參數，不填就是永久。** 設了之後，超過那個時間的原始紀錄在載入時被丟掉，檔案一併刪除——只從記憶體裡丟不會讓目錄停止長大。

**附件與 embedding 不落地。** 兩者都大、都不是人讀得懂的東西。但默默丟掉比不帶更糟，所以原本有附件的條目在 front matter 記下它有幾個。

**類別名 `FileMemoryStore`，與既有的 `InMemoryStore` 成對**——都是 `<後端>Store`，兩者讀起來是同一個家族的兩種後端。

考慮過並否決的做法：

- **SQLite。** Codex 的那一半。場域人員打不開一個 `.db`，而選檔案的整個理由就是他要看得到、刪得掉。將來要換後端，協定與 Playground 的記憶種類值都不必動——那個值命名的是記憶型態，不是後端。
- **Redis。** 要多顧一個服務，和「跑在晶片上的落地裝置」這個前提衝突。
- **只定介面不附實作。** 那一格解鎖了但按下去沒有東西，回到現況。
- **一個檔裝整段歷史。** 刪一則就得重寫整個檔，而刪一則是這個設計要支援的動作。

## Consequences

**部署時根目錄的位置是一個必須講明的設定。** Playground 跑在 Azure App Service 上，`/home/site/wwwroot` 每次部署會被整個換掉；根目錄要落在 `/home` 底下、`wwwroot` 之外，否則下一次部署就把記憶清空了。這一條要寫進部署文件。

**長對話會產生很多小檔。** 一則一個檔是刪除便宜的代價。把舊的原始紀錄收成主題會減少檔數，那是另一份工單。

**`memory_type` 那張字串表接不上這個實作**，因為它需要一個根目錄。目前只能以物件傳入 `Workflow`。宣告層與建構器的接線是另一份工單。

**`tier` 目前只有 `raw` 會被寫入。** `topic` 那一層由記憶層自己從原始紀錄合成，不佔用任何模組的位置，而合成是另一份工單；欄位先在這裡定好，免得之後要改已經寫出去的檔案格式。

**描述那一欄目前沒有人填。** 欄位定好了，也寫進每一個檔的 front matter，但填它的是合成主題那一步，而合成是另一份工單。約 150 字元是給那一步的準則，這裡沒有強制截斷——截斷一句話比留著一句長的更糟。

**刪掉一則的 API 還沒有。** 這份決議的理由是場域人員要刪得掉記錯的那一則，而目前能做的是手動刪那個檔（下一次載入就不見了）或整批 `clear`。Playground 上的清單與刪除是另一份工單。

**和 ADR-0002 有一處要講明。** 那份決議說更正一則已經交付的內容屬於持有對話紀錄的呼叫端，Playground 修剪自己的紀錄、下一輪從修剪過的版本建起。檔案式記憶不吃這一套：修剪呼叫端的紀錄不會動到磁碟上那個檔，下一次載入又把未修剪的那一則帶回來。要讓更正生效，得連同那個檔一起處理——而上一段說的那個 API 還不存在。這是這兩份決議之間的縫，不是 ADR-0002 被覆寫。

**根目錄在建構時就會被建出來。** 不能寫的根目錄在那一刻就失敗，而不是等到執行到一半第一次要寫入才失敗——那時已經有人在等回答了。
